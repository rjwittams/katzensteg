# Katzensteg WM Design

Date: 2026-04-30
Status: approved direction; implementation plan follows separately

## Goal

Add a `katzensteg wm` mode, or an equivalent separate app if the launcher gets too crowded, as an interactive terminal window manager for exercising the JSONL embed protocol.

The first coherent visual target is early Macintosh-like text chrome: monochrome/high-contrast window decorations, title bars, active/inactive state, keyboard-driven move/resize, and a small menu/status/debug area. This is inspiration, not emulation. The useful constraint is that the WM operates in terminal cells and makes geometry, focus, lifecycle, and cleanup obvious.

## Boundary

The WM owns all host UI and compositor behavior:

- window decorations
- title bars
- menus, status bars, debug bands, and accessory panes
- active/inactive window state
- move, resize, minimize, raise, lower, tile, and cascade behavior
- multi-producer session management
- mapping a producer's logical content rect into a terminal rect
- process lifecycle policy: detach, keep alive, terminate, kill-after-timeout

The Katzensteg producer owns only:

- capturing the target application
- emitting JSONL `frame_batch` messages for the requested content placement
- emitting cleanup batches for placements/images it produced
- responding to `attach`, `viewport`, `detach`, and `shutdown`

The WM asks a producer to render a logical window, initially `window_id = "main"`, into an inner content rectangle. The producer must not know or care that the host has a title bar, border, desktop, menu bar, status line, overlap policy, or debug pane around that rectangle.

This is not a request to push Mac-like UI concepts into the general Katzensteg runtime. General Katzensteg should learn only protocol/lifecycle primitives that are required between a host and a producer.

## Architecture

`wm` is a host/compositor layer above the existing attach/embed pieces.

- `launcher.zig` parses `katzensteg wm ...` and dispatches to the WM host.
- A new WM module owns terminal UI state, keyboard handling, producer sessions, placements, and lifecycle policy.
- Existing attach/embed helpers should be reused where they fit:
  - `attach_host.writeInitialControl` or a factored control-writer for `hello`/`attach`
  - `attach_protocol.parseFrameBatch` for producer output
  - `terminal_batch_applier.applyFrameBatch` for renderer-authored terminal bytes
  - `DirectTty` for terminal dimensions and raw terminal output
- The runtime and frame builder continue to treat `attach`/`viewport` rectangles as destination content rectangles, not decorated window rectangles.

The first implementation can live inside the launcher binary for ease of shipping. If it grows a real application shell, it can later become a separate executable while preserving the same internal host model.

## Core Objects

`WmHost`

Owns the terminal, input loop, render loop, producer list, focused window, and global shutdown.

`ProducerSession`

Owns one launched child process, stdin control writer, stdout JSONL reader, lifecycle state, upload policy/id ranges, and a bounded protocol event log.

`WmWindow`

Host-owned representation of one visible producer window. Initially each session has one `main` window. The WM window stores outer rect, inner content rect, title, focus state, z-order, and attachment state.

`Placement`

The host's terminal-cell placement for a `WmWindow`. In the first version this can be folded into `WmWindow`, but the design should leave room for one producer window to be attached to multiple host placements later.

`ProtocolEventLog`

Small ring buffer of host and producer events: launch, attach, viewport, frame batch, detach, detached, shutdown, exit, timeout, parse error. This should be visible in a debug accessory pane or status area early, because the whole point is to make lifecycle ordering debuggable.

## Visual Direction

Text decorations come first:

- single-cell line drawing for borders/title separators
- plain ASCII fallback if needed
- active window title emphasized, inactive title muted
- content rect clearly separated from chrome
- debug/status text outside producer-owned content

Themes are deliberately later:

- early Mac text chrome first
- later text styles: DESQview, GEM-ish, minimal debug
- graphic decorations only after protocol/window semantics are correct

## Staged Checklist

### Slice 1: Single Producer, Real Window Chrome

- `katzensteg wm <profile>`
- launch one owned producer as `katzensteg --embed-jsonl <profile>`
- draw a decorated text window
- attach `window_id = "main"` to the inner content rect
- render producer frame batches inside that content rect
- show a status/debug band outside the content rect
- quit sends `shutdown`, keeps reading for cleanup, then restores terminal

Protocol exercised:

- `attach`
- `frame_batch`
- `detach`
- `shutdown`
- cleanup drain
- host-owned terminal geometry

### Slice 2: Move/Resize Drives Viewport

- keyboard move window
- keyboard resize window
- clamp outer rect to terminal bounds
- recompute inner content rect from outer rect and text chrome
- send `viewport` when the content rect changes
- show current geometry in status/debug output

Protocol exercised:

- repeated `viewport`
- stale placement cleanup after geometry changes
- chrome/content coordinate separation

### Slice 3: Multi-Producer Early

- launch at least two profiles
- give each producer its own decorated window
- switch focus between windows
- show active/inactive chrome
- close can detach a window without killing its producer
- explicit terminate kills the selected producer session

Protocol exercised:

- multiple child processes
- multiple independent JSONL streams
- independent id ranges or allocation policy
- focus/lifecycle policy
- close vs detach vs terminate
- cleanup isolation between producers

### Slice 4: Window Manager Operations

- raise/lower
- overlap
- tile/cascade
- minimize/detach
- reattach minimized producer
- debug accessory window with recent protocol events per producer

Protocol exercised:

- reattach after detach
- placement occlusion assumptions
- lifecycle observability
- richer host state without runtime UI ownership

Occlusion note:

The WM currently uses host text for decorations and kitty graphics placements for producer content. That means overlapping windows are not a true composited surface: lower producer image placements can cover higher text chrome, and lower text decorations can show through transparent or unfilled areas of a higher producer window. Redrawing chrome, placeholder images, and kitty z ordering are useful diagnostics but are not a complete answer across terminals.

The likely long-term fix is host-owned occlusion: the WM computes covered content cells and tells producers which visible regions remain. Producers can then split placements or suppress fully covered regions before emitting batches, similar to how terminal multiplexers such as Zellij handle image overlap. Until that protocol exists, explicit tile/cascade layouts are the practical user-facing control for avoiding problematic overlap.

### Slice 5: Protocol Surface Expansion Modes

- relative placements
- producer-created child windows
- unicode/chrome torture mode
- alternate text border character sets
- text overlays/accessory panes
- intentional crash/hang/slow-cleanup profiles

Protocol exercised:

- multiple `window_id`s
- host/producer negotiation pressure
- unicode width correctness
- crash recovery
- orphan prevention
- cleanup fallback behavior

## Non-Goals For The First Pass

- no Pi extension changes
- no embedded inspector in this repo
- no runtime-owned decorations
- no graphical WM theme
- no socket/shared producer registry
- no mouse requirement
- no producer-created windows in the first PR

## Open Design Pressure

Multi-producer should arrive soon after the first slice, not as a distant future feature. It is the first point where the WM becomes a better protocol exerciser than `attach --exec`.

The likely first implementation should therefore avoid single-producer assumptions in names and data structures even if the first PR only launches one producer.
