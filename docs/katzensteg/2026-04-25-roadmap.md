# Katzensteg Roadmap

Date: 2026-04-25
Status: Working roadmap

This roadmap captures the direction after the first serious proof points:

- SDL applications can be interposed on macOS and mirrored into kitty/ghostty.
- Emulator workloads can be composed and played at useful speed.
- Moonlight can stream a real game into a terminal when forced through an SDL/software-rendered path.
- The inspector and profiling work have made the remaining gaps concrete rather than speculative.

The core direction is broader than "SDL preload renders to kitty". Katzensteg should become a small terminal graphics/runtime bridge with SDL preload as one adapter.

## Principles

- Keep the direct preload launch path useful. A user should still be able to run an app with `DYLD_INSERT_LIBRARIES` / `LD_PRELOAD` and get a result.
- Avoid split-brain rendering. The preloaded runtime should own terminal graphics, placement, chrome, and input injection. A launcher may supervise, but should not independently draw the screen.
- Keep protocol behavior centralized. Terminal capability detection, transport choice, placement identity, deletes, and image lifetime should not be scattered across SDL-specific code.
- Prefer evidence from real workloads, then isolate with small repros. RetroArch, ScummVM, Moonlight, and SDL tests are all useful in different ways.
- Preserve fallbacks. Experimental fast paths should degrade to slower but correct paths.

## Current Proof Points

### RetroArch / emulators

Framebuffer-like SDL workloads are viable, but often force full-frame composition. This has driven optimizations around composite copy, allocation reduction, and fullscreen presentation.

### ScummVM / standalone SDL apps

Katzensteg can run outside RetroArch and is useful as a general SDL interposer. Application-specific renderer behavior and startup races remain useful probes.

### Moonlight

Moonlight proves the concept can handle a real video stream:

```text
software H.264 decode
  -> swscale YUV to XRGB
  -> SDL texture upload/render/present
  -> Katzensteg capture/composite
  -> terminal graphics
```

This is intentionally not the final performance shape, but it proves the route is possible.

## Phase 1: Stabilize The Demo

Goal: make the current proof-of-concept paths reliable enough to use repeatedly.

- Keep RetroArch, ScummVM, Moonlight, and small SDL demos working.
- Fix crashers without panic reverts; root-cause first.
- Improve terminal reset behavior after crashes.
- Improve logging so one run explains renderer choice, output profile, frame size, texture formats, and transport.
- Make the `whiskers`-backed inspector functional enough to answer "what did the app render this frame?"
- Keep the embedded in-process inspector only as a fallback/debug path while `whiskers` becomes canonical.
- Resolve Retina / backing-pixel / logical-window coordinate bugs.
- Continue profiling-driven composite and capture optimization, but keep changes measurable.

## Phase 2: Input And SDL Window Policy

Goal: allow the terminal view to become the interactive surface.

- Capture terminal keyboard and mouse input in-process.
- Translate terminal input into SDL events.
- Map terminal mouse coordinates into SDL logical/window coordinates.
- Add policy for the real SDL window:
  - visible
  - hidden
  - offscreen/minimized
  - eventually possibly no real window, if SDL renderer paths tolerate it
- Keep the real window available for debugging and comparison.
- Add a thin launcher that sets environment, redirects logs, waits for the child, and restores terminal state, without owning screen drawing.

Phase 2 is the next focused design area.

## Phase 3: Runtime Boundaries / libkatzensteg

Goal: separate the reusable terminal graphics/runtime core from the SDL preload adapter.

Candidate internal modules:

- terminal capability detection
- kitty/ghostty profile selection
- image/session identity
- placement and deletion
- transport selection
- stats and diagnostics
- input mode setup/teardown
- SDL adapter

The long-term API should make direct TUI or agent CLI use plausible without pretending every caller is SDL.

## Phase 4: Chrome And Control Surface

Goal: allow Katzensteg to present more than the captured SDL image.

Examples:

- splash/status screen before the app produces frames
- stats overlay
- help overlay
- layouts where the SDL capture is smaller and terminal text surrounds it
- optional log tail from redirected stdout/stderr
- hotkeys for inspector/fallback capture, scaling modes, window policy, stats, pause, and reset

This should stay in-process so terminal drawing remains coordinated with image placement.

## Phase 5: Formats And Performance

Goal: reduce avoidable copies, scaling, and conversion costs.

Likely work:

- make YUV texture support explicit
- decide where YUV-to-RGB conversion should live for each workload
- add scalar and SIMD conversion paths
- investigate platform or GPU conversion backends
- avoid scaling when a full-screen source can be carried through at native size
- improve damage tracking / dirty regions
- keep allocation churn low with reuse and frame-lifetime arenas
- profile terminal transport costs separately from application decode/render costs

Moonlight is the main format/performance stress test. Hardware decode with an SDL frontend is a separate experiment from native VideoToolbox/Metal renderer interception.

## Phase 6: External Texture Future

Goal: move beyond "upload pixels to terminal" toward terminals importing external image/texture handles.

The serious end-state is a terminal graphics extension that can represent external surfaces:

- IOSurface-like handles on macOS
- dmabuf-like handles on Linux
- platform-specific handles elsewhere
- explicit size, format, color space, damage, lifetime, and sync/fence metadata

Katzensteg can lay the path by abstracting:

- capability negotiation
- image identity
- placement
- transport
- lifetime
- fallbacks

In that future, an agent or TUI could create a SwiftUI, Qt, Metal, Vulkan, WebView, or media-decoder surface and ask libkatzensteg how to expose it inside the terminal.

## Thin Launcher Role

The launcher should be useful but not central:

- choose the correct preload library for platform/architecture
- set presets for known apps
- redirect stdout/stderr to predictable logs or pipes
- pass config to the preloaded runtime
- wait for the child process
- reset terminal state on exit/crash
- report log paths and status

It should not own terminal rendering or draw chrome directly.

## Open Questions

- How much terminal keyboard fidelity can we get from kitty keyboard protocol, Ghostty behavior, and fallbacks?
- Should SDL event injection hook `SDL_PollEvent` / `SDL_WaitEvent`, use `SDL_PushEvent`, or both?
- Which real-window policy is safest across SDL renderers on macOS?
- Can hidden/offscreen windows keep gamepad and keyboard focus behavior acceptable?
- How should inspector control and runtime hotkeys share the terminal input stream?
- What is the smallest useful libkatzensteg API that is not overdesigned?
- How far can current kitty graphics z-order support take text-over-image chrome before we need to composite overlays into the image?
