# Luchs Implementation Plan

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `luchs` as a local visual fragment viewer with separate renderer and presenter backends, using SDL as the prototype presenter and native WebView as the current macOS HTML renderer.

**Architecture:** Keep `tools/luchs/` independent of Katzensteg internals for now. Renderer backends produce raw frames; presenter backends consume raw frames. The current concrete presenter is SDL, which keeps a normal window fallback and lets Katzensteg capture through its SDL adapter. Keep pushing on SDL for the prototype; a future presenter can call a proper app-facing Katzensteg core API once non-preload runtime initialization, sink selection, lifecycle, and non-SDL input/resize routing exist.

**Tech Stack:** Zig 0.15.2, SDL2, macOS `WKWebView` for native HTML rendering, later WebKitGTK on Linux, possible future `libkatzensteg-core` app-facing presenter.

## Chunk 9: Future Fragment And Embed Model

This is not part of the current prototype implementation plan, but captures the next design pressure from agent attach use cases.

- [ ] **Step 1: Define content identity separately from presentation**

Represent agent-provided fragments such as HTML, React, Markdown, Mermaid, images, or generated UI state as identified content objects.

- [ ] **Step 2: Define presentation requests**

Allow one content object to be presented multiple ways: inline terminal reflow, expanded Katzensteg side panel, another terminal pane, real SDL/WebKit window, or system browser.

- [ ] **Step 3: Define resize/cooperation semantics**

Decide how embed hosts resize cooperative content that can reflow and non-cooperative content that must be scaled, cropped, letterboxed, unloaded, or opened externally.
